## PART I: THE SYSTEM IN NATURAL ENGLISH

### 1.0 What the System Is

This system is a brain factory. It creates, trains, optimizes, evaluates, and manages multiple independent brains. Each brain is a self-contained unit of intelligence that consists of three parts: configuration, model, and bag of words. Everything in the system is represented as an executable tree structure. The system is aware of itself and can change itself over time, but only within boundaries that keep it stable and consistent.

The system has no dependencies on external libraries. It uses only traditional JavaScript with var, function statements, and for loops. It never uses arrow functions, forEach, map, or modern syntax. The system knows nothing about the shapes of data it processes; all shape information comes from configuration.

### 1.1 What the System Does

The system lets you create a brain by giving it configuration. You train the brain on data. You optimize the brain to make it better. You evaluate the brain to see how good it is. You test the brain with new inputs. You can have many brains at once. You can compare brains. You can combine brains into ensembles that work together. You can save brains to files and load them back. You can track different versions of each brain.

The system learns from text, from numbers, and from its own mistakes. It predicts what comes next: the next letter, the next word, the next number in a sequence. It finds patterns in data. It detects when patterns break. It generates strategies automatically. It builds abstract syntax trees from any input.

### 1.2 The Brain Triple

Every brain has exactly three parts that work together:

**Configuration** tells the brain how to behave. It contains the learning rules, the architecture specifications, the hyperparameters, the definitions of entities with their shapes using def@entity name:shape format, the definitions of actors who perform actions, the definitions of actions that can be performed, and the pipeline settings. Configuration is executable code that the brain follows.

**Model** is what the brain has learned. It contains trained parameters, weights, decision rules, pattern libraries, and strategy templates. The model is also executable code that takes input and produces output. The model grows and changes as the brain learns.

**Bag of Words** is the brain's vocabulary. It contains all the words and terms the brain knows, with their frequencies, their relationships, their n-gram statistics, and their context associations. The bag of words is also executable code that helps the brain understand text.

### 1.3 The Rule Hierarchy

The system follows rules at four levels, each with different authority:

**Level Zero rules are absolute and cannot be changed.** They are the constitution of the system. They include identity preservation, the requirement that every brain has all three parts, shape agnosticism, dependency freedom, traditional JavaScript only, self-model accuracy, evolution boundaries, and brain isolation. No brain can ever violate these rules. If a brain tries, it terminates itself.

**Level One rules govern how other rules can change.** They require consensus and validation. They include the rule modification protocol, learning rate governance, vocabulary growth policy, ensemble composition rules, performance benchmarking requirements, model evolution authorization, and resource quota enforcement. These rules can change, but only through careful consensus among many brains.

**Level Two rules are operational procedures.** They include the training protocol, prediction protocol, optimization protocol, evaluation protocol, serialization protocol, and version control protocol. These rules can evolve through meta-rule approval when they prove inadequate or when better ways are found.

**Level Three rules are adaptive and learned.** They include pattern recognition rules discovered from data, temporary strategies generated during optimization, and context-specific adaptations. These rules are created and modified freely as the brain learns, as long as they don't violate higher-level rules.

### 1.4 Core Operations

**Creating a brain** takes configuration, initializes an empty model, initializes an empty bag of words, assigns a unique identifier, and registers the brain in the system. The brain starts in untrained status.

**Training a brain** takes data, parses it into the executable tree format, updates the bag of words with new terms, extracts features using the bag of words, applies the training algorithm from configuration to update the model, calculates performance metrics, and marks the brain as ready.

**Optimizing a brain** takes a method like hyperparameter tuning, pruning, quantization, evolution, or ensemble creation. It creates candidate variations, tests them in simulation, selects the best, and applies it if it improves performance.

**Evaluating a brain** takes test data, runs predictions, compares to expected outcomes, and produces metrics including accuracy, precision, recall, F1 score, loss, confusion matrix, latency, and memory usage.

**Testing a brain** takes an input, parses it, extracts features using the bag of words, runs the model to get a prediction, calculates confidence, and returns the result.

### 1.5 Multi-Brain Management

The system can manage many brains at once. Brains are stored in a registry keyed by their unique identifiers. Brains can be listed, filtered by performance or tags or creation date. Brains can be cloned to create variants. Brains can be compared to see differences in configuration, model structure, vocabulary, and performance. Brains can be deleted when no longer needed.

Brains can form ensembles where multiple brains work together. Ensembles have their own configuration that specifies the combination method like voting or weighted averaging. Ensembles are themselves brains that contain references to their member brains. Ensembles can evolve by adding or removing members.

Brains maintain version history. Every successful evolution creates a new version. Old versions can be restored if needed. Versions can be compared to see what changed. The system keeps the last hundred versions by default.

### 1.6 Self-Awareness and Self-Evolution

The system is aware of itself. Each brain maintains a self-model that accurately represents its own state, its configuration, its model parameters, its vocabulary, its performance history, and its rule hierarchy. The self-model is executable code that the brain can query and analyze.

The system can change itself. When the brain detects opportunities for improvement, it generates candidate modifications. It simulates these modifications on historical data. It validates that they don't violate higher-level rules. It applies them if they improve performance. It verifies that the new state is consistent. It commits the change to version history.

Self-evolution is bounded. Evolution cannot go deeper than one hundred recursive steps. Evolution cannot add more than one thousand nodes in a single cycle. Evolution cannot happen more than ten times without stabilization. Simulation cannot take more than one hundred milliseconds. These bounds prevent uncontrolled growth.

### 1.7 Natural Language Understanding

The system understands natural language through grammar rules and a dictionary. Grammar rules define sentence structure: how words combine into phrases, how phrases combine into clauses, how clauses combine into sentences. The dictionary contains words with their definitions, parts of speech, and relationships to other words.

When the system reads English text, it parses it into a tree structure that represents the grammatical structure. It identifies entities, actions, actors, rules, instructions, and context. It extracts these elements and integrates them into its knowledge.

The system can read its own definition. When presented with this document, it will extract the shapes of brains, the rules at each level, the operations it can perform, the entities it manages, and the constraints it must follow. It will then configure itself according to what it read.

### 1.8 Technical Constraints

The system has no external dependencies. All code is self-contained. It uses only what JavaScript provides natively: objects, arrays, strings, numbers, functions, and the basic language constructs.

The system knows nothing about data shapes. It never references field names directly. All shape information comes from configuration using the def@entity name:shape format. The code asks the configuration what fields exist and accesses data through that indirection.

The system uses only traditional JavaScript. Variables are declared with var. Functions are defined with the function keyword. Loops use for with an index variable. There are no arrow functions, no forEach, no map, no filter, no reduce, no const, no let, no template literals. This ensures compatibility and predictability.

The system uses constructor functions and prototypes, not the class keyword. Objects are created with new and methods are defined on the prototype. This follows the classical JavaScript pattern.

### 1.9 What the System Can Parse

The system can parse any input into its executable tree format:

- Text becomes a tree of characters, words, sentences, paragraphs
- Numbers become a tree of values, sequences, ranges
- JSON becomes a tree of objects, arrays, properties, values
- CSV becomes a tree of rows, columns, cells
- HTML becomes a tree of elements, attributes, text
- Markdown becomes a tree of headings, paragraphs, lists, code blocks
- Natural language becomes a tree of sentences, phrases, words, parts of speech
- Configuration becomes a tree of settings, parameters, entity definitions
- Rules become a tree of conditions, actions, exceptions
- Instructions become a tree of steps, sequences, branches
- Code becomes a tree of statements, expressions, functions
- Its own definition becomes a tree of system specifications

The parser is universal. It looks at the input, detects the format, and applies the appropriate parsing rules. All parsing produces the same fundamental structure: nodes with types, values, children, attributes, and executable behaviors.

### 1.10 What the System Can Generate

The system can generate output in multiple formats from its internal tree representation:

- Text from a tree of words and sentences
- JSON from a tree of objects and arrays
- CSV from a table tree
- HTML from a document tree
- Markdown from a content tree
- Natural language from a meaning tree
- Code from an abstract syntax tree
- Strategies from goal trees
- Predictions from pattern trees
- Rules from extracted patterns
- New brains from configuration trees

The generator is universal. It takes any tree and serializes it to the requested format. The same tree can be output as JSON for machines, as text for humans, as HTML for web display, or as code for execution.
